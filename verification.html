Verification

Testing Strategies

I was responsible for testing the save state. LOVE2D also doesn't have any code coverage tools. These are condition coverage tests which ensure that the save state isn't corrupted and shouldn't produce negative numbers. We did not cover most of the code because it relies on user interaction and there is no way to automate user interaction within the LOVE2D framework.

Testing Infrastructure

I designed an interface that allows users to enter a testing mode with a key binding. Within the testing mode, users can select a simulated game state to start, and the game state starts from there while running asserts to check the save state doesn't get corrupted, and the text boxes are presented in the order they are supposed to. This saves us time by allowing us to just press a button instead of having to grind the game all the way to an end game state, or even from having to manually manipulate the save state to get to the end of the game. This also helped us catch that when paper production outpaced wood production in the early game, (only paper production was automated) the numbers representing wood collection to the user would wrap around and print a really big negative number instead of just zero.

Testing Technologies

We built our own testing paradigm. It allowed us to run the game from different save states where we could then automatically test whether certain variables were always within the proper bounds (the resources we collected should never end up as a negative number). It was effective in testing different states of the game and confirming our invariants but it was not effective in testing user interaction. I envision using this testing paradigm to quickly check any new features to our game won't cause any bugs or any changes to the math behind the progression won't make our numbers "wonky".
